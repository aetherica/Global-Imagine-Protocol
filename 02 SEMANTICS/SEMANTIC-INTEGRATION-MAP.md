# GIOP V3.1 — Semantic Pilot Integration Map

**Status:** VALIDATED FOR PILOT / NOT CANONICAL PROMOTION  
**Branch:** `v3.1-tree-architecture`

## Purpose

This record integrates the current pilot semantic entries without redefining the established GIOP architecture. It maps each newly authored concept to its primary semantic responsibility, required secondary connections, and boundary constraints.

The governing model remains:

`Visitor Universe → different entry depth → same canonical knowledge`

Repository placement is organizational; semantic responsibility is authoritative.

## Canonical Semantic Chains Preserved

### Measurement

`Scene / Object / System → Condition(s) → Measurement Procedure → Activity / Execution → Result → Representation`

The procedure specifies how an execution is carried out; the result is generated by that execution. The `has-result` relation connects those layers without collapsing them.

### Observation and presentation

`Result / Information → Representation → Display → Viewing Conditions → Observer → Perception`

Display remains a presentation mechanism. Representation remains information-bearing form. Observer and perception remain distinct semantic responsibilities.

### Computational realization

`Algorithm → Software Implementation → Execution → Result`

An algorithm is implementation-independent where possible; software realizes or implements an algorithm; execution is the run-time event/process; result is generated output.

### Temperature context

`Environment / Object / System → Temperature Condition → Temperature Quantity / Measurement → Result`

Physical temperature context is not silently substituted by color temperature or correlated color temperature.

### Viewing geometry

`Reference A ↔ Viewing Distance ↔ Reference B`

The relation carries the semantic connection; a Distance quantity may qualify its magnitude where applicable.

## Boundary Checks

1. No pilot entry converts a property, condition, quantity, relation, procedure, result, representation, or implementation into a class merely because it is important.
2. `Measurement Procedure` is not treated as the measurement activity itself.
3. `Result` is not treated as a quantity value or a representation.
4. `Display` is not treated as the representation it presents.
5. `Algorithm` is not treated as software.
6. `Software` is not treated as the algorithm it implements.
7. `Viewing Distance` remains a relation even when a numerical distance value is attached.
8. `Time` remains the temporal semantic foundation used by acquisition, execution, result, and presentation contexts.
9. `Temperature Condition` and `Temperature` remain distinct.
10. `has-result` connects execution contexts to generated results and does not silently imply measurement semantics in every execution.

## Integration Decision

The pilot set is semantically coherent enough to proceed to validation testing. No existing class set is expanded by this integration. The newly introduced semantic directories are treated as responsibility-oriented placements for pilot authoring, not as proof that repository folders themselves define the ontology.

## Promotion Constraint

These entries remain `Provisional` until the readiness gates and canonical promotion requirements are satisfied. This map therefore records integration, not final canonical admission.
